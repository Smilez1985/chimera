# Messung: DeepSeek-Anbindung im Gateway (13.11.2026)

**Stand:** `0d1b7a6` (Binaries aus CI-Lauf 43517760334, Prüfsumme
`484527d9d4cd…`), eingespielt am chimera-pi um 23:19, 13 Module ohne Fehler,
alle Einheiten `active`, `NRestarts=0`.

Gemessen wurde die **Kette**, nicht das Glück: Anbieter anlegen → Schlüssel
in die Ablage → Gateway fragt die echte API → Fehler kommt benannt zurück.

## Sandkasten, gegen die echte API (23:11)

Debug-Binary, eigene `CHIMERA_CONFIG_DIR`/`CHIMERA_STATE_DIR`, Anbieter
`ds` (`typ: deepseek`, keine Adresse ⇒ Vorgabe `https://api.deepseek.com`),
Schlüssel `sk-nur-ein-test` in `config/geheim/ds`:

| Op | Antwort |
|---|---|
| `modelle` | `schluessel_falsch`: „api.deepseek.com nimmt den Schlüssel nicht an (401) …" (vor der Schwärzung zusätzlich DeepSeeks Text mit `****test`) |
| `chat` | dito |

Damit belegt: TLS und DNS in Ordnung, `POST /chat/completions` und
`GET /models` gehen raus, `Authorization: Bearer` wird gesetzt, 401 wird als
**eigener** Code gemeldet.

**Fund dabei:** DeepSeeks 401 nennt die **letzten vier Zeichen des
Schlüssels** („Your api key: ****test is invalid"). Seit `0d1b7a6` gibt das
Gateway die Anbietermeldung bei 401 nicht mehr weiter — der Grund ist ohne
sie klar, und ein Schlüsselrest gehört in keine Antwort.

## Am Gerät (23:20)

Über `/run/chimera/tor.sock` als Nutzer `chimera`:

| Schritt | Antwort |
|---|---|
| `anbieter_setzen` `dstest` (`typ: deepseek`, ohne Adresse) | `{"ok":true}` |
| `schluessel_setzen` (Attrappe) | `{"ok":true,"neustart":true}` |
| `modelle` `dstest` | `schluessel_falsch` (401 von api.deepseek.com) |
| `chat` `dstest` `deepseek-flash` | `schluessel_falsch` (401) |
| `modelle` `ollama` (Gegenprobe) | 18 Modelle, `host 192.168.178.100:11434` — unverändert |

**Damit belegt:** Der Gateway-Prozess kommt vom Pi aus an
`api.deepseek.com` (die Unit hat keine `IPAddressDeny`), der Verteiler nach
`typ` greift, und der Ollama-Weg ist durch den Umbau nicht kaputt.

**Nicht belegt:** der Erfolgsfall. Dafür fehlt ein echter
`DEEPSEEK_API_KEY` — der Testschlüssel war eine Attrappe. Der Schlüssel
gehört nicht in den Chat; er kommt in `.env` (`DEEPSEEK_API_KEY=…`) oder
über das Modul „Anbieter" in `config/geheim/<id>`.

## Aufgeräumt

Anbieter `dstest` entfernt (`anbieter_entfernen`), Schlüsseldatei
`config/geheim/dstest` gelöscht. `config/anbieter/` enthält wieder nur
`ollama-192-168-178-100.json`, `config/geheim/` nur `ssh/`.
